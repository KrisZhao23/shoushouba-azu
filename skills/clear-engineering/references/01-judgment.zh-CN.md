# 工程判断：让条件真正改变选择

[English](01-judgment.md) | [简体中文](01-judgment.zh-CN.md)

用途：设计、重构、准备计划、发现责任或共享含义发生变化时阅读。这里提供推理关系，不要求每次填写同样的栏目。证据来源和限制见 [案例说明](06-case-evidence.zh-CN.md)。

## 1. 从可观察承诺形成整体结构

先明确谁要得到什么结果，结果何时算成立，什么不能被破坏。把流程中产生的事实、作出的决定和外部效果区分开，再寻找承担这些责任的现有位置。重要的不只是“有几个模块”，而是必要义务没有缺口、没有未经协调的多重解释。

功能目录描述系统有什么；职责解释为什么由它承担；行为路径解释各部分怎样合作；运行与失败关系解释在真实环境中是否仍然成立。它们不是同一张图，不能相互替代。无需全画出来，但在决定依赖相关关系时要能说明。

先选两三个具有区分力的情形来考验候选结构，例如正常完成、一个关键前提发生变化、一个真实失败。不是穷举未来；目的是辨别当前被接受的行为能否由候选责任组合实现。发现遗漏后回到责任或契约，而不只是追加例外条件。

SQLite 的架构与 pager 约束可用于研究“外部保证怎样被分配为跨层义务”，但不能推出所有项目都采用相同分层。Git 的稀疏索引可用于研究“共享表示变化如何影响旧消费者”，但不等于所有变化都需要兼容层。

## 2. 先区分变化性质，再决定边界

外部字段名变了而业务含义不变：让解释外部表示的位置吸收变化，检查对象身份、空值、单位、时区、默认值和失败语义是否真的保持。一个清楚的转换函数可以足够，不能由此推导工厂与接口家族。

业务含义变化：必须重新判断规则、状态消费者和存量解释，不能用字段映射假装适配完成。相同数值也可能已经代表不同生命周期。

运行环境或依赖版本变化：核对实际组合，问题可能只是已弃用参数、配置变化或启动路径，并不必然需要重做架构。Starlette 删除弃用参数的修复是限制过度设计的对照。

资源或失败语义变化：从同步变异步、从本地计算变远端调用，并非只有函数签名改变。取消、超时、重试、事务和生命周期要按实际语义重新判断。

具体如何辨认外部表示、隐形输入、导入副作用和生命周期，见 [07·A](07-implementation-boundaries.zh-CN.md#topic-a)；不是每个函数都增加参数，也不是每个来源都新增一层。

## 3. 责任内聚与独立变化发生冲突时

共同保护一项约束，不自动意味着所有实现必须放在一个文件。可以由清楚的事务、版本对应或协作契约保持关系；但必须有人承担最终判定、协调或冲突处理的责任，不能让约束悬空。

经常共同修改，不自动证明同一责任。共同需求、生成文件、格式化、组织分工和历史耦合都可能造成共同修改。研究变化原因和共享知识，而不只统计提交。

判断是否值得拆分，要问独立变化的压力在哪里、拆开后谁不再需要理解谁、组合代价增加多少。若只是把同样的隐含状态透传到更多函数，拆分没有得到预期收益。

判断是否值得合并，要问被分开的部分是否只是互相转发、任何变化都要求同步修改、没有独立契约或资源理由。允许删除没有保护作用的抽象；合并也不能把外部表示、业务政策和授权含义重新混为一谈。

## 4. 规则一致不等于唯一函数；状态归属不等于唯一进程

同一政策需要可辨认的解释依据和一致性保障。不同入口可以复用函数、调用同一服务、由同一规则生成，或使用独立但经过一致性核查的实现。跨信任边界重复校验可能必要。关键问题是政策是否被独立演变，什么变化要求同步，以及谁负责判断不一致。

同一状态可以有多个合法写入者，但要说明各自的权限、条件和冲突处理。区分权威事实、申请、建议、确认、缓存和展示投影；一个“完成”字段不能默认代表所有生命周期。

如果消费者决定业务动作时使用缓存，需确认缓存的时效与权威边界。如果缓存只用于展示，也要检查是否向用户显示了错误承诺。不能以“只是前端”自动免除相关含义判断。

## 5. 用事实处理复杂度冲突

| 争议 | 哪些事实改变选择 | 两端都应避免 |
|---|---|---|
| 合并还是分开 | 是否保护同一约束；独立变化是否真实；协调与定位成本 | 同名全合并，或文件长就拆层 |
| 复用还是重复 | 是否同一政策；是否跨信任边界；能否可靠同步含义 | 所有相似代码抽取，或每入口自行解释 |
| 保持旧契约还是统一迁移 | 旧消费者与旧数据是否存在；能否同步切换；兼容的期限和成本 | 默认永远兼容，或一改全体强制升级 |
| 重试还是先核实 | 操作可否重复；对端是否识别稳定操作；效果能否查询 | 超时直接重做，或所有超时永久停摆 |
| 现在多设计还是留待以后 | 已知约束、近期证据、不可逆后果、撤换与验证成本 | 只按差异行数省事，或为猜测建平台 |
| 继续调查还是停止扩展 | 相邻契约是否保持；关键反例是否处理；未知会造成什么后果 | 参数没变就停，或要求证明全系统无影响 |

这张表不是打分器。选择必须落在当前事实与备选方案的差别上。证据不足时可以选择可逆探索，或说明为什么仍不足以做高代价决定。

## 6. 外部效果、授权与长期工作是按条件触发的专题

有真实外部效果时，区分本地决定、请求发起、送达、对端效果、回执与最终确认。对端不支持去重或效果查询时，本地操作 ID 只能帮助关联，不能消除重复效果。补偿是新的动作，可能失败；取消本地等待也不等于取消对端操作。

涉及身份、缓存、导出、推送或后台动作时，沿着事实输出和实际效果检查授权。复用可信策略不等于把当前用户偷偷变成全局状态；后台操作需要自己的明确执行身份。原系统授权或模拟角色不能未经核实就当生产保证。

影响旧数据、旧协议或在途任务时，决定旧对象继续按旧含义、迁移、重算还是拒绝，并说明发生中断时如何判断现状。没有这类对象的小修改不强加迁移平台。

按需细化：[授权沿输出与效果延续](07-implementation-boundaries.zh-CN.md#topic-b)、[增量/撤销/关系修正与重放](07-implementation-boundaries.zh-CN.md#topic-c)、[确认内容与外部效果/存量补充](07-implementation-boundaries.zh-CN.md#topic-d)。这些是条件式工程建议，不是 Git 或任一项目证明了整套方法。

## 7. 计划并不是精确预测全部实现

先确定让他人能够衔接的承诺，内部实现保持可调整。计划粒度随未知和风险变化：未知资源能力先调查，已知共享契约先对齐，可逆私有组织可以边实现边修正。

每个提出计划的角色都应能解释本次在整体中的位置，而不是照抄一段通用“影响评估”。有效的大局观体现为发现相关生产者与消费者、保护共同约束以及合理限制范围。

不要因为发现新事实就认定原计划失败；也不要用“计划可以改”掩盖原本已知却忽视的重要约束。

## 8. 判断如何被推翻

为关键选择保留一个可检查的预期，例如“外部表示变化应主要留在转换处”“普通消费者仍获得旧路径含义”“允许编辑不应改变已批准发布内容”。后续变化若反复突破预期，检查原先的条件判断是否错误。

不要根据最终目录替初始设计补写理由。研究者推断与维护者原话分开；若有多种解释，保留不确定性。方法可被修正、拆细或删除，而不是不断增加例外来保护最初表述。
